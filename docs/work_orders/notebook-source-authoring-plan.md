## 대상 사용자 흐름

1. 같은 노트북에 처리된 기존 문서를 올리고 **스튜디오 → 문서 작성**에서 제안서 또는 보험 약관을 고른다.
2. 제안서는 **기존 제안서를 바탕으로 작성**을 고르고 기준 자료와 새 작성 목적을 지정한다. 기존 **제안요청서로 작성** 경로에서는 RFP와 참고 제안서를 서로 다른 입력으로 선택할 수 있게 한다. 기존 제안서 기반 작성에는 RFP를 필수로 두지 않는 안이다.
3. 약관은 상품 유형, 기준 약관 한 건, 반영할 변경점을 입력한다. 기준 문서 선택은 파일명이 아니라 읽을 수 있는 본문과 현재 노트북 접근 범위를 기준으로 한다. 1차 검수는 텍스트가 추출된 PDF·DOCX·TXT로 한다. 기존 제안서 동시 선택은 현재 소스 입력 상한인 10건을 넘기지 않는 안이다.
4. 확인 단계에서 파일명, 작성 목적이나 변경점, 작성 계획을 확인한다. 완료 후 실제 초안과 원문 근거 위치를 열 수 있고, 약관은 유지·수정·신규·삭제 제안을 확인할 수 있다. 공통 검수 형식은 DOCX이며 기존 RFP 경로의 출력 형식을 회귀 검증한다.

## 개발 단계와 검수 기준

| 단계 | 변경 및 산출물 | 실패 재현과 합격 기준 |

| 1. 작성 입력과 버전 계약 | `authoring/templates.py`, `template_data/`, `session.py`, `service.py`, `studio_v2_routes.py`, Studio V2 OpenAPI. 단계 1의 입력·버전 계약을 확정한 뒤 단계 2와 3을 연결한다. 영향 범위 API 및 마법사 시험, OpenAPI 계약, 타입·빌드 검사와 종단 검수 기록을 한 변경 단위로 남긴다. QA에는 합성 문서와 격리 계정을 쓰고, 완료 후 시험 노트북·산출물·임시 파일의 정리를 확인한다.

## 승인 경계와 되돌리기

- 계획 승인 항목은 RFP 없이 시작하는 제안서 작성 경로, 기준 약관 한 건 선택, 입력·응답의 호환 확장이다. 기존 저장 구조로 설계하며 DB 마이그레이션은 현재 계획에서 예상하지 않는다. 승인 전에는 구현, 실모델 호출, 배포를 시작하지 않는다. 실제 비용이나 ysna 반영이 필요하면 해당 범위를 확인한다.
- 새 입력 경로를 되돌려야 하면 변경 PR을 revert한다. 작업을 진행하기 전에 이전 버전이 새 작성 리비전을 안전하게 조회할 수 있는지, 실행 중인 큐가 종료된 뒤 코드만 되돌릴 수 있는지 시험해 복구 절차를 확정한다. 저장된 사용자 산출물은 보존한다.
- 완료는 세 사용자 경로의 결과물과 근거가 검수되고 실패·권한 경계와 기존 기능 회귀를 확인했을 때 판정한다.

| 경로 | 로컬 검수 증거 |

API·작성 작업자·관련 회귀 124건, 하위 시험 56건 통과. FastAPI 라우트, Studio 작업자, 내보내기 코드를 실제 실행했으며 외부 모델과 PostgreSQL 저장소는 대역을 썼다. 워커는 큐 등록 뒤 소스 권한이 취소된 경우 모델 호출 전에 중단했다. 실제 DOCX 바이트로 후반 문단과 근거 재열기를 검사했다. 마법사·Studio 클라이언트 38건, 변경 화면 TypeScript 구문 및 린트, Studio v2와 v1 OpenAPI 계약이 통과했다. 사용자 설명서의 웹·DOCX·PDF를 기존 빌더로 갱신하고, 본문과 배포 manifest의 해시 일치 및 설명서 회귀 21건을 확인했다.

PostgreSQL 통합 시험 12건은 전용 시험 DB 연결 설정이 없어 건너뛰었다. 실제 모델, 로그인한 제품 브라우저에서 업로드부터 결과를 확인하는 전 과정, 전체 Next.js 빌드, ysna는 미검증이다. 세 경로의 실환경 검수 후 병합 판정을 한다.

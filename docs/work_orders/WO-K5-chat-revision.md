## 1. 목표

완료된 자료를 열어 둔 채 LLM과 대화하면서 "어디를 어떻게 수정해 줘"라고 말하면 고칠 수 있어야 한다.

WO-K4 원칙을 그대로 따른다.

| 맡는 쪽 | 일 |
| --- | --- |
| **LLM (판단)** | 지시를 이해하고, 고칠 위치와 새 내용을 정하고, 자료가 더 필요한지 판단한다 |
| **제품 (관리와 심부름)** | 자료와 지시를 전달하고, LLM이 요청한 자료를 찾아 주고, 전·후를 보여 주고, 저장한다 |
| **사람 (결정)** | 지시하고, 수정안을 보고 반영할지 정한다 |

## 2. 신산님 결정

| # | 결정 |
| --- | --- |
| C-1 | 대상은 문서 작성, 보고서, 슬라이드, 플래시카드, 퀴즈 5종이다 |
| C-2 | LLM의 수정안은 **확인 후 반영**한다 |
| C-3 | 제품은 지시의 종류를 미리 제한하지 않는다. LLM 능력으로 못 하는 것은 LLM이 못 한다고 답하며, 그때 자료는 바뀌지 않는다 |
| C-4 | LLM에게서 **바뀐 부분만** 받는다 |
| C-5 | 수정에 새 자료가 필요하면 **LLM이 판단해 찾게 한다** |

| --- | --- | --- |

| 문서 작성 저장 형식 | 소목차별 문단 목록. `{text, refs, origin}`. 표를 담을 수 없음 | `authoring/session.py` `edit_unit` |

| 작업 큐 | 시작·재시도·종료 때 자료 상태를 generating·queued·종료 상태로 바꿈. 작업 중인 자료는 수정 불가 | `studio_v2_queue.py` `start`, `retry`, `finish`, `sweep` |
| 자료 찾기 | `StudioKnowledge.extend`가 승인 지식을 찾아 새 근거 번호를 붙임. 빈 계획이어도 기본 검색을 함 | `studio_knowledge.py` |
| LLM 호출 시간 | Media-Bridge 30초 제한. 대화 수정에서의 실제 시간은 미측정 | `WORK_STATUS.md` |

## 4. 사용 흐름

1. 완료된 자료 화면에 "대화로 수정" 입력창이 있다. 작업 중인 자료에는 입력할 수 없다.
2. 사용자가 지시를 입력한다. Enter로 보내고, 한글 조합 중 Enter는 무시한다.
3. 작업 큐가 지시를 처리한다. 화면은 진행 중임을 표시한다. 브라우저를 닫아도 처리는 이어진다(K-7).
4. 결과는 대화창에 표시된다.
   - **수정안이 있을 때:** LLM 답변과 조각별 고치기 전·후를 보여 주고 "반영", "취소" 버튼을 둔다.
   - **수정안이 없을 때:** LLM 답변만 보여 준다. 질문을 되묻거나 못 한다고 답한 경우다.
5. "반영"을 누르면 새 버전으로 저장한다. "취소"를 누르면 자료는 그대로이고 대화에는 취소로 남는다.
6. 사용자는 이어서 지시할 수 있다. 나갔다 돌아와도 대화가 이어진다.

## 5. 구조

### 5.1 자료 조각

제품은 자료를 번호 붙은 조각으로 펼쳐 LLM에 주고, 돌려받은 조각만 끼워 넣는다.

| 자료 | 조각 번호 | 내용 |
| --- | --- | --- |
| 보고서 | `title`, `summary`, `s{n}.heading`, `s{n}.b{m}`, `s{n}` | 제목, 요약, 절 제목, 블록(문단·목록·표), 절 전체 |
| 슬라이드 | `title`, `s{n}` | 제목, 슬라이드 전체 |
| 플래시카드 | `c{n}` | 카드 전체 |
| 퀴즈 | `q{n}` | 문항 전체 |
| 문서 작성 | `{소목차키}.title`, `{소목차키}.p{n}` | 소목차 제목, 문단 |

수정의 종류는 `replace`, `insert_after`, `delete` 세 가지다. 절이나 슬라이드를 통째로 추가·삭제하는 지시도 같은 방식으로 처리한다.

새 파일 `studio_chat_edit.py`에 펼치기와 끼워 넣기를 둔다. 저장 전 정리는 기존 `validate_user_edit`를 그대로 쓴다.

### 5.2 LLM 호출

C-5에 따라 호출은 많아야 두 번이다.

1. **자료 판단(자료를 찾을 수 있을 때만):** 지시와 자료 목차를 주고 새 자료가 필요한지 묻는다. 필요 없다고 답하면 찾지 않는다.
2. **수정안 작성:** 다음을 주고 JSON으로 받는다.
   - 입력: 지시, 이 자료의 최근 대화 6턴, 자료 조각 전체, 찾은 자료
   - 출력: 아래 형식

```json
{
  "reply": "사용자에게 보여 줄 답변",
  "changes": [
    { "op": "replace", "id": "s3.b2", "content": { "type": "paragraph", "text": "새 내용", "refs": ["S1"] }, "reason": "바꾼 이유" }
  ]
}
```

- 시스템 지시에는 "지시받은 부분만 고칠 것, 할 수 없으면 `changes`를 비우고 이유를 `reply`에 쓸 것, 없는 내용을 지어내지 말 것"을 넣는다.
- 찾는 범위는 이 자료에 연결된 노트북 Source와 노트북에서 고른 승인 지식이다. 둘 다 없으면 자료 판단을 건너뛴다.
- 노트북 Source는 기존 `build_pack`으로 지시와 관련된 구간을 읽는다. 승인 지식은 기존 `StudioKnowledge`와 같은 경로와 횟수 상한(8회)을 쓴다. 다만 자료 판단에서 필요 없다고 답하면 기본 검색도 하지 않는다.
- 지금 자료의 근거 번호와 이번에 찾은 근거 번호만 쓸 수 있다. 그 밖의 번호는 저장 때 지워진다.
- LLM 호출 비용과 외부 전송 정책은 기존 스튜디오 LLM 호출 경로를 그대로 따른다.

### 5.3 저장 (마이그레이션 `0083`)

새 테이블 `studio_v2_edit_turns`를 둔다.

| 열 | 내용 |
| --- | --- |
| `tenant_id`, `workspace_id`, `turn_id` | 기본 키 |
| `output_id` | `studio_v2_outputs` 참조, 자료와 함께 삭제 |
| `owner_actor_id` | 지시한 사용자 |
| `base_revision` | 수정안을 만든 기준 버전 |
| `instruction` | 지시. 2,000자 이하 |
| `state` | `queued`, `working`, `ready`, `no_change`, `failed`, `applied`, `discarded` |
| `reply`, `changes_json`, `new_evidence_json` | LLM 답변, 수정안, 새 근거 |
| `error_code`, `applied_revision` | 실패 코드, 반영된 버전 |
| `idempotency_key_sha256` | 같은 지시 중복 처리 방지 |
| `created_at`, `updated_at` | 시각 |

조직·작업 공간 격리와 권한은 `0074` 스튜디오 테이블과 같은 방식으로 둔다.

### 5.4 작업 큐

기존 `studio_v2_jobs`와 워커를 그대로 쓴다. 임대, 재시도, 사용자별 동시 실행 제한을 다시 만들지 않기 위해서다.

- 작업 요청의 `mode`를 `chat_edit`로 둔다.
- `chat_edit` 작업은 `start`, `retry`, `finish`, `sweep`에서 **자료 상태를 바꾸지 않는다.** 수정안을 만드는 동안 자료는 완료 상태로 남는다.
- 워커는 `chat_edit`이면 새 리비전을 만들지 않고 결과를 `studio_v2_edit_turns`에 저장한다.
- 재시도를 다 써서 실패하면 대화 턴을 `failed`로 바꾼다.

### 5.5 API

기존 스튜디오 경로 아래에 둔다. 모두 `Action.EDIT` 권한이 필요하다.

| 요청 | 동작 |
| --- | --- |
| `POST /outputs/{output_id}/edit-turns` | 지시 등록. 202. `Idempotency-Key` 필수 |
| `GET /outputs/{output_id}/edit-turns` | 이 자료의 대화 목록 |
| `POST /outputs/{output_id}/edit-turns/{turn_id}/apply` | 수정안 반영. 201과 새 버전 번호 |
| `POST /outputs/{output_id}/edit-turns/{turn_id}/discard` | 수정안 취소. 204 |

OpenAPI 계약, BFF 허용 경로, 웹 API 클라이언트를 함께 갱신한다.

### 5.6 화면

- 새 컴포넌트 `studio-chat-edit.jsx`를 스튜디오 자료 상세와 문서 작성 완료 화면에 붙인다.
- 문구는 기존 메시지 파일에 넣는다. 화면 코드에 한글을 직접 쓰지 않는다.
- 전·후 비교는 조각 단위로 보여 준다.

## 6. 반영

공통으로 `base_revision`이 현재 최신 버전과 같은지 확인하고, 다르면 저장하지 않는다.

| 자료 | 반영 방법 |
| --- | --- |
| 보고서, 슬라이드, 플래시카드, 퀴즈 | 조각을 끼워 `validate_user_edit`로 정리하고 새 리비전 저장. 이전 근거를 잇고 새 근거를 추가한다. 리비전 기록에 `edited_by=llm_chat`와 지시를 남긴다 |
| 문서 작성 | 조각을 끼우고 문단 `origin`을 `chat`으로, 바뀐 소목차를 `locked`로 둔다. 이어서 기존 `reopen`, `resume` 경로로 근거·용어 점검을 다시 돌린다 |

- 사람이 직접 고쳐 잠긴 소목차도 대화 지시로는 수정안을 만들 수 있다. 반영 여부를 사람이 정하기 때문이다.
- 문서 작성은 점검이 도는 짧은 동안 자료가 작업 중 상태가 된다.

## 7. 오류 처리

| 상황 | 동작 |
| --- | --- |
| LLM 답의 형식이 틀리거나 없는 조각 번호를 가리킴 | 1회 다시 요청. 그래도 실패하면 턴을 `failed`로 하고 안내. 자료는 그대로 |
| 끼워 넣은 결과가 저장 규칙을 어김 | 1회 다시 요청. 그래도 실패하면 위와 같음 |
| 자료 찾기 실패 | 대화를 끊지 않고 찾지 못했다는 사실을 LLM에 알려 답하게 함 |
| LLM 호출 실패 | 작업 큐의 기존 재시도 규칙을 따름 |
| 반영할 때 자료가 이미 바뀜 | 저장하지 않고 "자료가 바뀌었으니 다시 지시해 주세요" 안내 |
| 자료가 작업 중 | 지시 등록과 반영을 거부 |
| 진행 중인 턴이 이미 있음 | 새 지시를 거부. 한 자료에 한 번에 한 지시만 처리 |
| 자료 전체가 입력 한도 초과 | `CHAT_EDIT_TOO_LARGE`로 안내. 한도는 자료 조각 합계 60,000자 |

## 8. 시험과 완료 기준

| 단계 | 기준 |
| --- | --- |
| 자동 시험 | 5종 조각 펼치기·끼워 넣기, 수정안 검증, 재요청, 버전 충돌, 반영, 권한, 큐가 자료 상태를 바꾸지 않음 |
| 실제 서버 시험 | 5종 모두 대화로 수정·반영하고 새 버전과 내보낸 파일에 반영됨을 확인. 못 하는 지시에 `changes` 없이 답하는 경우 확인 |
| 문서 시험 | **1→5→10페이지** 문서에서 대화 수정 성공. 10페이지의 소요 시간과 Media-Bridge 30초 제한 측정 |
| 자료 찾기 | 새 자료가 필요한 지시에서 노트북 Source와 승인 지식을 찾아 근거 번호가 붙은 수정안이 나옴 |
| 이어가기 | 나갔다 돌아와도 대화와 대기 중 수정안이 남아 있음 |

## 9. 구현 단계

단계별로 병합하고, ysna 배포는 단계마다 승인받는다.

| 단계 | 내용 | 완료 조건 |
| --- | --- | --- |
| 1 | 조각 펼치기·끼워 넣기, 마이그레이션, 큐 `chat_edit`, 수정안 작성, API | 자동 시험과 실제 서버 시험으로 보고서 수정·반영 성공 |
| 2 | 슬라이드, 플래시카드, 퀴즈, 문서 작성 반영과 점검 | 5종 실제 서버 시험, 1→5→10페이지 |
| 3 | 자료 찾기 연결 | 새 자료가 필요한 지시 성공 |
| 4 | 화면 | 신산님 화면 확인 |

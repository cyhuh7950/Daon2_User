## 1. 원칙

**제품은 철저하게 중간 관리자이자 심부름꾼이다.** 제품에는 지능이 없으므로 내용을 판단하지 않는다.

| 맡는 쪽 | 일 |
| --- | --- |
| **LLM (판단)** | 목차·구성 제안, 템플릿 최적화, 필요한 자료 판단, 어떤 지식을 어떻게 쓸지 선택, 본문 작성 |
| **제품 (관리와 심부름)** | LLM에 물어보기, LLM이 고른 지식 호출, 쓸 수 있는 범위 제한, 승인 확인, 횟수·비용 제한, 진행 관리, 사람에게 확인받기, 기록, 근거·형식 검증 |
| **사람 (결정)** | 시작할 때 구성 확정, 필요할 때 자료·본문 수정, 최종 확인 |

Codex·Claude Code처럼 LLM이 전체 작업을 주도하는 구조가 아니다. 주도권은 제품이 쥐고, **판단이 필요한 순간마다 LLM에 묻는다.**

## 4. 공통 구조

모든 산출물이 같은 엔진을 쓴다. 다른 것은 구성 단위와 출력 형식뿐이다.

```text
요청
 → (1) 작업 계획: LLM이 구성안 작성 또는 템플릿 최적화
 → (2) 사람 확정
 → 단위마다 반복
    (3) 자료 계획: LLM이 필요한 지식과 찾는 방법을 선택
    (4) 심부름: 제품이 범위를 넣어 호출, 승인 확인, 결과 정리
    (5) 작성: 찾은 자료로 LLM이 작성
    (6) 검증: 제품이 형식과 근거 확인, 자료 없는 부분 표시
    (7) 저장: 단위별 결과와 근거 스냅샷 저장
 → (8) 사람 최종 확인
```

### 4.1 자료 계획의 형식

LLM은 도구 호출 기능이 아니라 일반 응답의 JSON으로 답한다. 지금 동작하는 LLM 경로만으로 되고, 도구 호출이 되는 경로가 생기면 이 단계만 교체한다.

```json
{
  "needs": "이 소목차를 쓰는 데 필요한 것",
  "requests": [
    {"knowledge": "rag", "package": "P1", "query": "평가 기준과 배점"},
    {"knowledge": "ontology", "package": "P1", "query": "품질 관리"},
    {"knowledge": "ruleset", "package": "P1", "query": "제안서 필수 항목"}
  ]
}
```

- 제품은 **지금 쓸 수 있는 선택지 목록**(지식 종류, 설명, 업무 패키지 별칭)을 만들어 LLM에 준다. 승인·게시되지 않은 지식은 목록에서 뺀다.
- LLM은 프로젝트 ID, 업무 패키지 ID, 토큰을 모른다. 제품이 별칭을 실제 값으로 바꿔 호출한다.
- 목록에 없는 지식이나 패키지를 요청하면 그 요청만 버리고 기록한다.
- 계획 응답을 해석하지 못하면 사용자 문장으로 RAG를 검색한다. 호출 자체가 실패하면 답변을 만들지 않고 오류를 표시한다(WO-K3 D2).

### 4.2 지식 선택지

| 종류 | 호출하는 도구 | 쓰임 |
| --- | --- | --- |
| `rag` | `search_document_evidence` | 문서 원문 근거 |
| `graphrag` | `graphrag_query` | 개념과 관계를 따라가는 답 |
| `ontology` | `ontology_search_concepts`, `ontology_get_concept`, `ontology_traverse` | 용어 정의와 연결 |
| `ruleset` | `ruleset_list`, `ruleset_get`, `ruleset_evaluate` | 지켜야 할 규칙과 판정 |
| `approved` | `approved_knowledge_search`, `approved_knowledge_read` | 게시된 지식 자산 |

### 4.3 안전 규칙

- LLM의 요청은 데이터로만 다룬다. 제품이 정한 도구만 실행한다(§7A.8).
- 호출은 질문 또는 단위당 최대 8회, 검색어는 최대 3개로 제한한다.
- 자료 계획은 문서 본문을 보기 전에 끝낸다. 문서 속 지시문이 검색을 조종하지 못하게 하기 위해서다.
- 외부 응답 본문은 신뢰하지 않는 데이터로 전달한다.
- 자료 계획 호출에는 질문, 목차, 패키지 이름만 보낸다. 근거 본문은 보내지 않는다.

### 4.4 근거 없는 내용

LLM이 찾지 못한 내용을 지어내지 못하게 한다. 문장마다 근거를 달게 하고, 근거 없는 부분은 `[자료 없음]`으로 표시한다. 표시된 단위는 사람에게 알린다.

### 4.5 사람이 개입하는 지점

| 지점 | 기본 동작 |
| --- | --- |
| 작업 계획 후 | 문서 작성은 반드시 확인. 스튜디오는 기본 건너뜀, 선택 시 확인 |
| 자료 계획·검색 후 | 자동 진행. 선택 시 확인 |
| 단위 작성 후 | 자동 진행. `[자료 없음]`이나 검증 실패가 있으면 멈추고 알림 |
| 전체 완성 후 | 근거 없는 부분과 검증 결과를 보여 주고 확인 |

### 4.6 끊기지 않고 이어지는 구조

가장 중요한 요구다(K-7).

- 작업은 **단위별 상태를 저장한 하나의 실행**이다. 각 단위는 `대기 → 자료 계획 → 자료 확보 → 작성 → 검증 → 완료` 또는 `사람 확인 대기` 상태를 가진다.
- 진행 위치는 메모리가 아니라 저장소에 둔다. 서버가 재시작돼도 완료된 단위는 다시 하지 않고 다음 미완료 단위부터 이어진다.
- 사람이 끼어들면 그 시점에 **일시 정지**한다. 진행 중인 단위까지만 마치고 멈춘다.
- 사람이 목차, 자료, 본문을 고치면 고친 내용을 **기준값으로 고정**한다. 이후 LLM이 덮어쓰지 않는다.
- 사람이 빠지면 **다음 미완료 단위부터 자동으로 이어진다.** 고친 내용은 다음 단위의 요약과 용어 목록에 반영한다.
- 사람이 앞부분 구조를 바꾸면 영향받는 단위만 다시 대기 상태로 돌린다. 영향 범위는 사람에게 보여 주고 확정받는다.
- 어느 단위에서 실패해도 전체를 버리지 않는다. 그 단위만 실패로 표시하고 재시도하거나 사람에게 넘긴다.

1단계 채팅은 질문 1개가 1단위라 저장 대상이 없다. 공용 엔진은 단계별로 나눠 만들어 3단계 문서 작성에서 이 구조를 그대로 쓴다.

### 5.1 문서 작성의 템플릿

- 시작할 때 LLM에 요청과 자료 설명, 템플릿(있으면)을 주어 이번 문서에 맞게 최적화한다. 템플릿이 없으면 처음부터 만든다.
- 사용자는 템플릿과 달라진 점을 보고 확정한다.

| LLM이 고칠 수 있음 | LLM이 고칠 수 없음 |
| --- | --- |
| 소목차 구성, 순서, 분량 배정, 작성 지침, 필요한 입력 | 필수 조항·필수 절, 검증 규칙, 쓸 수 있는 지식 범위, 출력 형식 |

- 템플릿에서 사용할 도구 목록을 없앤다. 자료 선택은 4.1 단계가 맡는다.
- 소목차마다 목표 분량을 주고, 앞에서 쓴 내용의 요약과 용어 목록을 다음 소목차에 넘긴다.
- 소목차별로 저장해 하나만 다시 쓸 수 있게 한다.
- 전문 검증은 그 검증이 정의된 템플릿에서만 동작한다. 임시 템플릿에는 근거 검증과 `[자료 없음]` 표시만 적용된다.

## 8. 변경 영향

- **외부 전송:** 자료 계획 호출에 별도 판정이 필요하다. 지금 승인 구조는 실행당 전송 내용 하나만 묶기 때문에, 계획 호출용 판정 경로를 추가한다.
- **비용:** 단위마다 LLM 호출이 2회가 된다. 비용 제한이 켜진 작업공간에서는 계획 호출까지 집계해야 한다.
- **DB:** 근거 스냅샷을 지식 종류별로 담도록 넓혀야 할 수 있다. 문서 작성의 소목차별 저장은 현재 저장 구조를 구현 단계에서 확인한다. DB 변경이 필요하면 따로 승인받는다.
- **정본:** 승인 후 설계서 §7A.4, §7A.5.1, §7A.8과 개발 계획서에 반영한다.
